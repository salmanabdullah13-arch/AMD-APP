19a: the BOM request builds a real job BOM, and it becomes the budget

Salman was right that this was modelled wrongly. It asked "is this a
standard, or the numbers for one job?" with ONE JOB'S NUMBERS as the
blocked option — exactly backwards from what Operations wants, which is
the BOM for an approved job so the project budget can be set before work
starts.

The request, the budget and the production gate are now one chain: he
builds the BOM, submitting it sets the department budget, Operations
approves it, and that approval is already what opens production.

It was cheap because computeBOMTotals() only ever reads r.amount per
line, so real multi-line arrays work with the existing rollup, the BD
5,000 threshold and the gate untouched.
finaliseDepartmentBudgetSubmission() is extracted so the two writers
cannot drift.

Materials come from the Item Master (free text refused — an unlinked
line cannot be reserved) at cost, never selling price. Labour is days x
men with no rate field anywhere; the amount is applied at submit from
the department payroll average, and his screens show man-days. Joinery
and paint are one screen and one submit, two budgets underneath.

Pull-from-estimate re-reads rates from the Item Master rather than
copying the quotation's, and says so where they differ.

A BOM never travels as an answer payload — the request is closed with a
pointer, because money would be refused by the whitelist and again by
the database trigger, and both refusals are right.

Design review caught a lock-out: the form is keyed on an OPEN request,
so refusing the five-box form for itemised budgets would leave a
REJECTED one with no editable path. The request select is optional now.

Real bug found while verifying: nextJobCardNo() was length-based, so it
minted an existing id the moment the array had a gap — and the 25 Aug
purge put gaps in it. The insert failed on the primary key, getJobCard()
returned the OLD job, and the lane gate correctly refused "No BOM".
Max-based now, like every other id generator here.
